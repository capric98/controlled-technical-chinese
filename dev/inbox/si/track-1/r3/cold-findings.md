# 冷读审阅 · track-1 · r3（被审文本：dev/inbox/si/track-1/r2/SKILL.md）

模式：review；文档类型：agent 指令；歧义阈值：strict。
严重级别按被审文本 §6 的级别映射：必须 = ERROR，应 = WARNING，可以 = STYLE；未使用 §8 的升级条款。

## 第一部分：finding 列表

### F1
规则：CTC-A005
严重级别：ERROR
位置：「**行为** — 全部规则生效。」（§3 strict）；「A、P 两族按其记录级别生效，歧义阈值更高」（§3 standard）
问题：strict 写「全部规则生效」，standard 只写 A、P 两族「按其记录级别生效」，§3 开头只补了 S、L、T 三族。R 族（含必须级的 CTC-R001）在 standard 下是否生效，文本没有说。与 strict 的「全部」对照，可以读出「standard 下并非全部规则生效」。
风险：执行 standard 任务时，一种读法照常应用 CTC-R001–R006，另一种读法跳过 R 族（例如不做 CTC-R003 的去译文腔，或不以 CTC-R001 约束改动）。两种读法产出不同的改写。
建议修改：在 §3 开头写明「三种模式下全部规则都生效，模式只改变歧义阈值」，并删去 strict「行为」中的「全部规则生效。」。

### F2
规则：CTC-A005
严重级别：ERROR
位置：「**情态强度的模糊同样按本节处理**。改写时，规范性指令中由无判据词（见 CTC-R004）承担义务的条件，按 CTC-R004 在「待确认」中提出：列出其可能的两种以上强度并给出建议，然后停手」；「- 尽快回滚 | 「尽快」承担义务，强度未定 | 作者意图的规范强度 | 可读作「必须立即执行」或「应在窗口内执行」，建议按前者确认」
问题：CTC-R004 与「待确认」第 4 类处理的是缺判据的判定条件（「无判据的规范条件」「不得补出来源没有的判据」）；§5 却把同一情形写成情态强度的模糊，要求列出几种可能的强度。示例两头都占：「失败后尽快回滚」里义务已经很清楚（祈使句），缺的是时限判据，但给出的两种读法同时改了强度（必须／应）和判据（立即／窗口内），其中「窗口」来源里没有。
风险：遇到同一个无判据词时，一种执行问作者要多强的义务，另一种问作者要什么判据。「待确认」的内容因此不稳定，建议栏还会带进来源没有的判据。
建议修改：改为「由无判据词承担的判定条件，按 CTC-R004 在「待确认」中列出缺失的判据；只有该词同时让义务强度无法确定时，另列可能的强度并给出建议」。示例的问题栏改为「「尽快」未给出回滚时限」，需要的信息栏改为「回滚时限或触发时点」。

### F3
规则：CTC-A005
严重级别：ERROR
位置：「级别与严重级别一一对应」（§6）；「唯一允许的升级：一条「应」级违规可以按 ERROR 报告」（§8）；「review 模式下，任一项偏离都是一处 finding，严重级别由所引规则的级别决定。」（§9）
问题：§6 和 §9 把级别到严重级别的映射写成没有例外；§8 却允许「应」升为 ERROR。§9 的核对表还是 review 模式的另一个 finding 来源，它说严重级别「由所引规则的级别决定」，没有提到升级。
风险：「风险」字段指名了不同动作的「应」级违规，可能按 §8 报为 ERROR，也可能按 §6／§9 报为 WARNING；从 §9 核对出来的 finding 能不能升级，也无法确定。
建议修改：§6 改为「级别决定默认严重级别，唯一的升级见 §8」；§9 改为「严重级别按 §8 确定」。

### F4
规则：CTC-A005
严重级别：ERROR
位置：「只有在存在多个可能执行者且不同读法改变由谁执行时才补出执行者」（CTC-A001）；「只有多角色交替执行时才补主语。」（§10 第 1 条）
问题：两处都用「只有……才」给补出执行者／主语设了唯一条件，但条件不同。CTC-A001 的条件是有多个可能执行者、且读法会改变由谁执行；§10 的条件是多角色交替执行。只有一个角色、但执行者仍不确定的句子满足前者，不满足后者。
风险：碰到这类句子，一种执行按 CTC-A001 补出执行者，另一种按 §10 不补。两处都是必须／不得级表述，每个结果都会被另一处判为违规。
建议修改：§10 第 1 条改为「只有存在多个可能执行者、且不同读法改变由谁执行时才补主语（CTC-A001）。」

### F5
规则：CTC-A005
严重级别：ERROR
位置：「「直到…为止再继续」必须仍是继续的前提」；「合并后它必须仍是**由操作者执行**、位于被守护动作**之前**、且**逐项列全**原有判据的确认动作」（CTC-P003，级别：应）
问题：CTC-P003 的级别是「应」。按 §6 的定义，它是可被更高优先级或明确边界推翻的默认要求，违反报 WARNING。规则内部却有两处「必须」，并把违反结果称为「删除校验点」。这两项要求到底能不能推翻、违反时报 WARNING 还是 ERROR，都无法从文本唯一重建。
风险：不同审阅者把同一个被降为附注的阻塞判据分别报为 WARNING 和 ERROR。改写时，一种执行可能以更高优先级为由推翻阻塞性质，另一种则不会。
建议修改：把「保持阻塞性质」和「合并后校验三要件」写成不可推翻的要求，并注明违反时同时构成 CTC-L003（时序）或 CTC-S001（断言集合）的违规。规则其余部分保留「应」。或者把这两处「必须」改为「应」，并说明推翻它们需要满足什么边界。

### F6
规则：CTC-A005
严重级别：ERROR
位置：「未发现问题时返回「未发现违规」，其后最多三条 STYLE 观察，每条引用规则 ID。」（§8）；「只返回 finding 列表，不返回整篇文本。」（§3 输出契约）
问题：一条引用规则 ID、且对应规则确实被触发的 STYLE 观察，本身就是一条 STYLE 级 finding（CTC-R006 可以 → STYLE）。文本没有说清三件事：STYLE 级违规算不算「问题」；STYLE 违规超过三条时全部列出还是只列三条；「观察」用不用六字段格式。
风险：同一份只有排版问题的文本，一种执行逐条列出全部 STYLE finding，另一种返回「未发现违规」加至多三条自由格式观察。编排者无法按统一格式解析结果。
建议修改：改为「未发现 ERROR 或 WARNING 级 finding 时，先写「未发现违规」，其后按六字段格式列出 STYLE 级 finding，最多三条」。如果作者本意是「观察不是 finding」，就明确写出「观察」与 finding 的区别和格式。

### F7
规则：CTC-R001
严重级别：ERROR
位置：「**情态强化**（CTC-S003；语域清理另归 CTC-R003）」；「正例：在生产环境部署该服务前，请确保已配置环境变量。」
问题：这个示例演示的是 CTC-S003，而 CTC-S003 只要求保留「请确保」的请求强度，不要求任何改动。正例却另做了几处改动：删掉两个「你」，把「如果你想在……部署」改为「在……部署前」（意愿条件变成了时间前提），删掉「中」，把「已经……了」改为「已」。CTC-R003 列出的触发项只有被动、名词化赘语、过长的「的」字串、英语从句语序残留和直译连接词，没有删人称代词和「已经……了」；「语域清理」也不是任何一条规则的触发条件。示例用来演示单条规则，自己却做了无法逐处归因的改动，与 CTC-R001 和 §10「原样返回来源是合法的输出」相矛盾。
风险：模仿这个正例的执行会把「语域清理」当成改写许可，做不引用规则的等义替换；把意愿条件改成时间前提，还会碰到 CTC-L001 的条件保持要求。
建议修改：正例改为「原样返回。「请确保」保持请求强度（CTC-S003）。」如果要演示 CTC-R003，另立一例，逐处标注每项改动对应的触发项。

### F8
规则：CTC-P005
严重级别：WARNING
位置：「本技能生效：§3 中 strict 与 standard 适用范围所列的文档、状态提示」
问题：§3 两个适用范围里都没有「状态提示」，strict 只列了「告警与错误信息」。这句可以读作「状态提示是 §3 所列类别之一」，但事实并非如此；也可以读作「状态提示在所列文档之外单独适用」，那样它就没有对应的模式，§1 的模式推定对它无法执行。frontmatter 的 description 同样没有列出状态信息。
风险：处理状态提示时，一种执行用 strict 的歧义阈值，另一种用 standard 的阈值，或者判定本技能根本不适用。
建议修改：把 strict 适用范围改为「告警、错误与状态信息」，并同步修改 description；或者删去 §1 的「、状态提示」。

### F9
规则：CTC-R004
严重级别：WARNING
位置：「选择顺序：调用方给出的术语约定 > 来源中最明确且出现最多的形式 > 来源中首次出现的形式。」
问题：第二级判定条件靠「最明确」这个无判据词成立，而且用「且」和「出现最多」合取。最明确的形式与出现最多的形式不是同一个时，第二级可能没有候选，文本没有说此时是否降到第三级。
风险：同一份来源，一种执行选出现最多的形式，另一种选它自认为最明确的形式，还有一种降到首次出现的形式。统一出来的术语因执行者而异。
建议修改：改为「来源中出现次数最多的形式（次数相同时取首次出现的形式）」；如果要保留「明确」，就给出可观测的判据，例如「带中英对照定义的形式」。

### F10
规则：CTC-R004
严重级别：WARNING
位置：「补出目标语言必需的显性成分（量词、连接词、话题标记）在不引入新命题时不算新增」（§7 翻译）；「**不得补出省略的量词。**」（§10 第 7 条）
问题：翻译条款允许补出「必需的」量词，但「必需」没有判据。§10 第 7 条不分任务类型，一律禁止补量词，它的反例「发送一个心跳包」恰好是英译中时常被当作「必需」补出的形式。两处的边界无法从文本唯一确定。
风险：翻译 "send a heartbeat packet" 时，一种执行按 §7 写「发送一个心跳包」，另一种按 §10 写「发送心跳包」，而且每一种都会被另一处判为违规。
建议修改：§7 写明判据，例如「省略后不合汉语语法的成分才算必需」；§10 第 7 条改为「不得补出语法上可省略的量词」。

### F11
规则：CTC-T001
严重级别：WARNING
位置：「本规则不要求每句都有显性主语。」（CTC-A001）；「**不得要求每句都有显式主语。**」（§10 第 1 条）
问题：同一个概念用了「显性主语」和「显式主语」两个称呼。
风险：「显式」在文中另用于「显式化」这个概念（§2、CTC-R002），读者可能把两个称呼当成两个不同的概念。
建议修改：统一为「显性主语」，把 §10 第 1 条改为「不得要求每句都有显性主语。」

### F12
规则：CTC-R006
严重级别：STYLE
位置：「| strict / standard | 只返回改写后的中文正文。」（§3 输出契约表）；「在 strict／standard 下是内部纪律」（§3）
问题：并列模式名之间的斜杠混用半角斜杠加空格和全角斜杠（「改写／翻译／审阅／新写」「strict／standard／review」用全角）。
风险：只影响排版一致性，不影响语义。
建议修改：统一为全角斜杠：「| strict／standard | 只返回改写后的中文正文。」

## 总体判断

不可发布。阻塞项：F1–F7 为 ERROR，其中严重级别映射自相矛盾（F3）、执行者补出条件冲突（F4）、§5 与 CTC-R004 处理对象不一致（F2）、情态示例的改动无法归因（F7）必须先解决。
